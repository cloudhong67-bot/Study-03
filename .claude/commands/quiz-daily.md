`prisma/data/questions.json`을 점검하고, 카테고리 `$0`(비었으면 모든 카테고리)의 문제를 **모두 새 문제로 교체**해 줘. 새 문제는 기존 문제 어느 것과도 겹치면 안 된다.
아래 1–7단계를 **순서대로** 진행한다. 단계마다 "통과 조건"을 확인하고, 하나라도 어긋나면 **그 자리에서 멈추고** "실패 보고" 형식으로 보고한다. 다음 단계로 넘어가지 않는다.
CLAUDE.md의 "퀴즈 문제 교차 검증 가이드라인"과 "Data and migrations" 규칙을 지킨다. 문제 작성 규칙(난이도 기준, 문체, 정답 위치)은 `.claude/commands/quiz-add.md`와 같다. 그 파일을 읽고 따른다.

## 인자 확인

- 교체할 카테고리: `$0` (앞뒤 공백은 무시한다). 비었으면 `CATEGORIES`의 모든 카테고리다.
- 값이 있으면 `prisma/seed.mjs`의 `CATEGORIES`에 있는 `name` 중 하나여야 한다. 목록은 추측하지 말고 파일에서 읽는다.
- 허용값이 아니면 아무것도 하지 않는다. 사용법(`/quiz-daily`, `/quiz-daily 과학`)과 허용되는 카테고리 목록을 보여 준 뒤 멈춘다.
- 문제마다 출처 2곳으로 교차 검증해야 하므로 전체 교체(40문제)는 오래 걸린다. 시작할 때 교체할 문제 수를 알리고, 나눠서 하려면 카테고리를 지정하라고 안내한다.

## 공통 규칙

- JSON은 Node로 읽는다. 줄 단위 grep으로 문제를 세거나 고르지 않는다.
- 단계마다 결과(수치, 확인한 항목)를 기록해 두었다가 7단계 보고에 쓴다.
- 파일을 고치는 단계는 5단계 하나뿐이다. 1–4단계에서는 아무것도 쓰지 않는다.
- seed, 마이그레이션, 테스트 코드는 고치지 않는다.
- **교체는 같은 id 자리에서 한다.** 문제마다 `id`, `category`, `difficulty`는 그대로 두고 `question`, `options`, `answer_index`, `explanation`만 바꾼다.
  - 세션이 참조하는 문제는 DB 트리거가 삭제와 id 변경을 막는다. 그래서 새 id로 추가하고 옛 문제를 지우는 방식은 쓰지 않는다. 내용 수정은 허용되고, seed가 id로 upsert한다.
  - 난이도를 유지하므로 3·4·3 균형과 최대 점수(카테고리 217, 전체 모드 817/821)가 바뀌지 않는다.

## 1단계: 파일 구조 읽고 이해하기

- `prisma/data/questions.json`을 읽고, `prisma/seed.mjs`에서 `CATEGORIES`(카테고리 이름 목록)와 `validateQuestions`(검증 규칙)를 읽는다.
- 문제 객체의 필드와 순서(`id`, `category`, `difficulty`, `question`, `options`, `answer_index`, `explanation`)와 서식(2칸 들여쓰기, `options`는 한 줄 배열, 파일 끝 줄바꿈)을 확인한다.
- `git status --short prisma/data/questions.json`으로 커밋하지 않은 변경이 있는지 본다. 변경이 있으면 보고에 적는다. 이것만으로 멈추지는 않는다.
- **통과 조건**: 파일이 있고 JSON 파싱에 성공하며, 최상위가 배열이고, 모든 객체가 위 7개 필드를 가진다.

## 2단계: 현재 문제 개수와 분포 확인

Node로 아래 값을 구한다.
- 전체 문제 수, id 최솟값·최댓값, id 중복 여부
- 카테고리별 문제 수, 카테고리 × 난이도(`easy`/`medium`/`hard`) 개수
- 카테고리별·전체 정답 위치(0–3) 개수
- **통과 조건**: id 중복이 없고, 모든 `category`가 `CATEGORIES`에 있으며, 모든 `difficulty`가 허용값이다. 어긋난 문제가 있으면 id와 함께 실패로 보고한다. 기존 데이터가 깨진 상태에서는 교체하지 않는다.

## 3단계: 교체 대상 정하기

- **교체 대상**: 대상 카테고리에 속한 모든 문제다. 카테고리 `sortOrder` 순으로, 카테고리 안에서는 id 순으로 정렬한다. 대상마다 (id, 카테고리, 난이도)를 적는다.
- **정답 위치 계획**: 교체 후 카테고리마다 정답 위치 0–3이 고르게(10문제면 2–3개씩) 나뉘도록 대상마다 위치를 미리 정한다.
  - id 순서로 같은 위치가 3번 연속되지 않게 한다. 교체하지 않는 문제와 붙는 경계도 포함한다.
  - 보기가 수치 순서인 문제는 오름차순을 지키고, 정답 위치는 그 순서를 따른다. 이 경우 4단계에서 계획한 위치와 달라질 수 있다. 다른 대상의 위치를 조정해 분포를 맞춘다.
- **통과 조건**: 교체 대상이 1개 이상 정해졌다.

## 4단계: 교체 전 기존 문제와 중복 체크

대상마다 `quiz-add.md`의 규칙대로, 그 자리의 난이도에 맞는 새 문제 초안을 만든다. 초안마다 아래를 모두 확인하고, 중복은 배제한다.
"기존 문제"는 교체 전의 `questions.json` 전체를 말한다. 이번에 교체될 문제도 포함한다. 같은 주제를 표현만 바꿔 다시 내는 것은 교체가 아니다.

- **기계적 중복**: Node로 기존 문제 전체와 비교한다.
  - 공백·문장부호를 빼고 비교했을 때 `question`이 같은 문제가 없다.
  - 새 문제의 정답 문자열이 같은 카테고리 기존 문제의 정답과 같지 않다.
  - 새 문제의 정답이 기존 문제의 질문·해설에 핵심어로 나오지 않는다(예: 기존 해설에 나온 "서희"를 정답으로 묻는 문제).
  - 이번에 만든 초안끼리도 같은 방식으로 비교한다.
- **의미 중복**: 같은 카테고리의 기존 문제(질문·정답·해설)와 다른 초안을 읽고, 같은 인물·사건·개념을 다른 말로 묻는지 판단한다. 예를 들어 기존 #1 "훈민정음 창제 왕"과 "한글을 만든 왕"은 중복이다. 겹치는 기존 문제가 있으면 그 id를 적는다.
- **사실 검증**: 정답과 해설의 사실(연도, 수치, 인물, 장소)은 WebSearch로 **서로 다른 출처 2곳 이상**에서 확인한다. 오답 3개가 어떤 해석으로도 정답이 될 수 없는지도 확인한다. 확인하지 못한 주제는 버리고 다른 주제로 바꾼다.
- **통과 조건**: 모든 초안이 위 세 검사를 통과했다.
  - 중복이 나온 초안은 배제하고, 주제를 바꿔 다시 만든다. 대상 하나당 3번까지만 시도한다.
  - 3번 안에 통과하지 못하면 중복으로 실패 보고한다. 이때 대상 id, 겹친 기존 id, 시도한 주제를 함께 적는다.
- 통과하면 **카테고리마다** 교체표를 보여 주고, 교체할지 **사용자에게 확인받는다**. 승인 없이는 5단계로 넘어가지 않는다.
  - 교체표 열: id · 난이도 · 기존 질문/정답 → 새 질문/정답 · 정답 위치
  - 교체표 뒤에 초안 JSON과 검증 근거를 붙인다.
  - 사용자는 카테고리 단위나 문제 단위로 일부만 승인할 수 있다. 승인된 것만 5단계에서 교체하고, 나머지는 기존 문제를 그대로 둔다.
  - 사용자가 모두 거절하면 아무것도 바꾸지 않은 채 멈추고, 그때까지의 결과를 보고한다.

## 5단계: 문제 교체 후 형식 검증

1. **원본 보존**: 파일을 고치기 전에 Node로 원본을 그대로 복사한다(`fs.copyFileSync`). 복사본은 `backups/quiz-daily/<YYYYMMDD-HHmmss>/questions.before.json`에 두고, 시각은 한국 시간을 쓴다. 원본과 복사본의 SHA-256이 같은지 확인한다. 다르거나 복사에 실패하면 파일을 고치지 않고 멈춘다.
2. **교체**: Edit로 승인된 문제 객체마다 `question`, `options`, `answer_index`, `explanation` 줄만 바꾼다. `id`, `category`, `difficulty` 줄과 객체의 위치는 그대로 둔다. 기존 서식을 따르고, `JSON.stringify`로 파일 전체를 다시 쓰지 않는다.
3. **형식 검증**: Node로 파일을 다시 읽어 `validateQuestions`와 같은 규칙을 확인한다. JSON 파싱, id 중복 없음, 알려진 카테고리, `question`·`explanation`이 비어 있지 않음, `options` 4개이며 서로 다른 비어 있지 않은 문자열, `difficulty` 허용값, `answer_index` 0–3 정수. 이에 더해 아래도 확인한다.
   - 문제 수와 id 순서가 원본과 같다.
   - 모든 문제의 `id`, `category`, `difficulty`가 원본과 같다(카테고리 × 난이도 분포 불변).
   - 승인되지 않은 문제는 내용이 원본과 똑같다(id별로 비교).
   - 교체한 문제는 `question`이 원본과 다르다. 4단계의 기계적 중복 검사를 교체 후 파일 전체에 다시 돌려도 통과한다.
   - 카테고리마다 정답 위치가 0–3에 고르게 나뉘고, id 순서로 같은 위치가 3번 연속되지 않는다.
   - `git diff --stat prisma/data/questions.json`으로 보면 바뀐 줄이 교체한 문제의 내용 줄(문제당 최대 4줄)뿐이어야 한다.
4. **실패 시**: 위 검증 중 하나라도 실패하면 고쳐서 넘어가지 말고, `questions.before.json`으로 파일을 되돌린다. 되돌린 파일의 SHA-256이 원본과 같은지 확인한 뒤, 실패 보고를 한다.
- **통과 조건**: 3번의 검증이 모두 통과했다.

## 6단계: 전체 데이터 백업

5단계에서 만든 `backups/quiz-daily/<시각>/` 폴더에 아래를 더한다.
- `questions.after.json`: 교체를 마친 `questions.json`의 복사본
- `db.sql`: 로컬 DB 전체 덤프. 먼저 `docker compose ps db`로 db 컨테이너가 실행 중인지 확인한다. 실행 중이면 `docker compose exec -T db pg_dump -U trivia -d trivia --no-owner`의 출력을 Node로 받아 파일에 쓴다. 비밀번호는 명령이나 파일에 적지 않는다.
  - db 컨테이너가 꺼져 있으면 DB 덤프는 건너뛴다. 이 경우 "DB 백업 생략(컨테이너 꺼짐)"으로 보고하되, 실패로 보지는 않는다. 문제 파일 백업만 해도 충분하기 때문이다.
  - 컨테이너가 켜져 있는데 덤프가 실패하거나 결과가 비어 있으면 실패다.
- `manifest.json`: 만든 시각(KST), 파일마다 크기와 SHA-256, 문제 수, 교체한 id 목록
- **검증**: 백업 파일을 다시 읽어 SHA-256이 manifest와 같은지 확인한다. `questions.after.json`은 현재 `questions.json`과 같아야 한다. `db.sql`은 `CREATE TABLE`과 `quiz_sessions`, `scores` 테이블 정의를 포함해야 한다.
- `backups/`는 `.gitignore`에 들어 있어 커밋되지 않는다. DB 덤프에는 닉네임 같은 플레이 기록이 들어 있으니 공유하지 않는다. `git status --short`에 `backups/`가 보이면 실패로 보고한다(백업이 커밋될 수 있는 상태).
- **통과 조건**: 위 검증이 모두 통과했다. 실패해도 `questions.json`은 되돌리지 않는다. 교체는 이미 검증을 마쳤기 때문이다. 백업 실패만 보고한다.

## 7단계: 실행 결과 상세 보고

한국어로, 아래 순서대로 출력한다.

1. **요약**: 단계별 결과 표(단계 · 결과(통과/실패/생략) · 핵심 수치 한 줄), 교체한 문제 수와 id, 승인되지 않아 남긴 id
2. **교체 전·후 분포** (표): 카테고리 · easy · medium · hard · 합계 · 정답 위치 0/1/2/3. 난이도 분포는 같아야 하고, 정답 위치는 전과 후를 나란히 적는다.
3. **교체한 문제**: 카테고리마다 교체표(id · 기존 질문/정답 → 새 질문/정답), 그리고 문제마다 JSON 객체(코드 블록), 검증 근거(사실마다 출처 2곳 이상의 제목과 URL), 정답 위치를 고른 이유, 중복 체크 결과(가장 가까운 기존 문제 id와 다른 점)
4. **백업**: 폴더의 전체 경로, 파일별 크기와 SHA-256, DB 백업을 했는지(생략했다면 이유)
5. **영향과 다음 단계**:
   - 최대 점수와 3·4·3 균형은 바뀌지 않는다는 확인
   - **기존 플레이 기록 영향**: 같은 id의 내용이 바뀐다. 따라서 진행 중인 세션은 문제 도중에 다른 문제를 받을 수 있다. 지난 결과 화면에서는 새 문제 옆에 옛 선택이 보인다. 점수와 정답 여부는 `session_answers`에 저장돼 있어 바뀌지 않는다. 걱정되면 반영 전에 진행 중인 세션이 없는지 확인하라고 안내한다.
   - `npm run db:seed`로 로컬 DB에 반영하고 `npm test`로 테스트가 그대로 통과하는지 확인하라는 안내. 테스트는 정답을 DB에서 읽으므로 점수 기대값은 바뀌지 않아야 한다.
   - 되돌리는 방법: `questions.before.json`을 `prisma/data/questions.json`으로 복사한 뒤 `npm run db:seed`를 실행한다.
   - 새 문제를 다시 검증하려면 `/quiz-check <카테고리>`와 `/quiz-validate`를 실행하라는 안내

## 실패 보고

어느 단계에서든 실패하면 즉시 멈추고, 아래 형식으로만 보고한다.

1. **실패한 단계**: 번호와 이름
2. **오류 내용**: 어긋난 통과 조건, 실제 값, 관련 문제 id나 파일 경로, 명령의 오류 메시지(그대로 인용)
3. **현재 상태**: `questions.json`이 바뀌었는지(5단계에서 되돌렸다면 되돌린 뒤의 SHA-256 확인 결과), 만든 백업 파일 목록
4. **이전 단계 결과**: 통과한 단계와 그 핵심 수치
5. **해결 방법**: 사용자가 할 일(예: `docker compose up -d db`, 깨진 문제 id 수정) 그리고 다시 실행할 명령
